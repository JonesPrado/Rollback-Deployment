Git é a fonte da verdade

No modelo GitOps, o rollback nunca é um comando manual dentro do cluster — é uma operação Git (reverter um commit no repositório de configuração). O ArgoCD apenas observa esse repositório e faz o cluster convergir para o que está escrito nele.

// 01 — contextualização

O que é rollback, afinal?

Para entender rollback, primeiro é preciso entender deploy: é o processo de colocar uma nova versão de um sistema em funcionamento para os usuários. Um sistema está na versão 1.0, os desenvolvedores lançam a 2.0 — ela passa por testes e depois é enviada para produção, o ambiente onde os usuários de fato utilizam o sistema.

O problema é que uma nova versão pode apresentar erros: falhas no login, problemas em pagamentos, funcionalidades que deixam de funcionar. Quando isso acontece, a equipe pode realizar um rollback — fazer o sistema voltar para uma versão anterior que estava funcionando, saindo da 2.0 e retornando para a 1.0. Isso recupera a estabilidade rapidamente enquanto a equipe investiga e corrige o problema.

Em DevOps, o rollback importa porque não basta colocar novas versões em produção rapidamente — é preciso também ter uma forma segura de recuperar o sistema quando alguma alteração dá errado.

Analogia — Minecraft

Imagine que você construiu uma cidade inteira e, antes de uma grande alteração, criou um backup do mundo. Se depois você perceber que destruiu uma parte importante da cidade, pode restaurar o backup e voltar ao estado anterior.

O rollback funciona de forma parecida: uma nova versão é instalada, algo dá errado, e o sistema retorna para a versão anterior que estava funcionando. A diferença é que, em sistemas reais, o rollback pode envolver não apenas código, mas também configurações, containers, bancos de dados e outros componentes da aplicação.

// 02 — aplicações

Onde é usado e pra que serve

1. Onde é usado

  • Kubernetes — mecanismo nativo via kubectl rollout undo. É o caso mais estudado e documentado.
  • GitOps / ArgoCD — rollback tratado como operação Git (reverter commit no repositório de configuração), não como comando manual no cluster.
  • CI/CD em geral — GitLab CI, Jenkins, Spinnaker também suportam rollback automatizado ou manual quando um deploy falha.
  • Serverless / PaaS — Heroku, AWS Lambda, Vercel, Netlify guardam versões anteriores prontas pra reativação.
  • Bancos de dados / migrações — camada separada, tratada com técnicas específicas (expand-contract), não é um "desfazer" simples.
  • Estratégias de deploy — Blue-Green e Canary são desenhadas para tornar o rollback quase instantâneo (troca de roteamento, não reversão de código).

2. Pra que serve

  • Recuperação rápida de incidentes — reverter sem precisar corrigir código sob pressão.
  • Redução de MTTR (tempo médio de recuperação) — reverter costuma ser mais rápido que debugar em produção.
  • Segurança operacional — dá confiança para deployar com mais frequência.
  • Auditoria e histórico — permite entender o que mudou entre versões.
// 03 — modelo consolidado

As 4 camadas de rollback

Nem todo rollback custa igual. A pesquisa consolida o tema em quatro camadas — quanto mais perto do dado real do usuário, mais caro e arriscado fica reverter.

Camada O que reverte Mecanismo Custo / risco
1. Código-fonte (Git) Histórico de commits git revert / git reset Baixíssimo
2. Deployment / Imagem (Kubernetes) Qual ReplicaSet está ativo kubectl rollout undo — troca de ponteiro, não reconstrói nada Baixo, mas limitado pelo revisionHistoryLimit (padrão: 10 revisões)
3. etcd (estado do cluster) Todo o estado administrativo (Deployments, Services, Secrets, ConfigMaps) etcdctl snapshot save/restore — exige parar apiserver e etcd Alto — afeta o cluster inteiro. Usado só em disaster recovery
4. Dados de runtime (banco / volumes) Dados gerados durante a execução da aplicação Padrão expand-contract (expandir → migrar → contrair) Alto — reverter uma etapa é garantido; reverter várias de uma vez, não
Resumo do padrão

As camadas 1 e 2 são baratas e quase sem risco — é mudança de referência/metadado. As camadas 3 e 4 são caras e arriscadas: a 3 porque afeta o cluster inteiro, a 4 porque dados reais de usuários não são simplesmente "desfeitos".

// 04 — detalhe técnico

Kubernetes — o rollback da Camada 2

  • Cada mudança de Deployment cria um novo ReplicaSet; o Kubernetes mantém histórico de revisões.
  • kubectl rollout undo não reconstrói containers nem baixa imagem de novo — apenas troca o ponteiro do Deployment para o ReplicaSet anterior.
  • O número de revisões guardadas é controlado por revisionHistoryLimit (padrão: 10). Passado esse limite, a revisão antiga se perde e não pode mais ser restaurada com undo.
Armadilha comum

O rollback muda o estado do cluster, mas não corrige o arquivo YAML de origem. Se o pipeline reaplicar o YAML antigo (com bug), o cluster volta pro estado ruim — a menos que o Git também seja corrigido, mantendo cluster e repositório sincronizados.

// 05 — camadas 3 e 4

etcd e dados de runtime

etcd — o que é e quando entra (Camada 3)

  • etcd é o único componente com estado do Kubernetes: guarda todos os objetos de API (Deployments, Services, ConfigMaps, Secrets, RBAC).
  • Um backup do etcd é suficiente para restaurar o cluster inteiro.
  • Restaurar um snapshot é invasivo: exige parar o kube-apiserver e o etcd, mover o diretório de dados antigo, restaurar o snapshot em um novo diretório e só então reiniciar os serviços.
  • Usado em cenários de falha catastrófica do control plane, migração de cluster, ou erro humano que afetou múltiplas aplicações — não é o mecanismo usado para reverter o deploy de uma única aplicação.

Dados de runtime e o padrão Expand-Contract (Camada 4)

Runtime = qualquer dado criado ou modificado enquanto a aplicação está em execução (registros de banco, uploads, sessões, cache, logs). Esses dados não voltam sozinhos quando você reverte a imagem — é o ponto mais arriscado do rollback.

1️⃣
Expand
Adiciona novos elementos de schema ao lado dos existentes, sem quebrar nada.
2️⃣
Migrate
Transiciona dados e lógica gradualmente para o novo schema.
3️⃣
Contract
Remove os elementos antigos — só depois que a migração está validada.
Regra-chave: N / N-1

A versão nova da aplicação deve ser compatível com o schema anterior, e vice-versa. Limitação importante: cada etapa individual pode ser revertida, mas reverter várias etapas de uma vez não é garantido.

// 06 — o gatilho do deploy

Merge, tag, release — e onde entra o GitOps

Antes de disparar um deploy (e, futuramente, um rollback), é preciso saber exatamente o que dispara o quê.

merge na main

Avança o código. É o gatilho mais comum de deploy contínuo (ex: deploy automático em staging).

tag

Um "apelido fixo" para um commit específico. Diferente de uma branch (que se move), a tag aponta sempre para o mesmo commit.

release

Uma tag "vestida" pela interface do GitHub: changelog, anexos, marcação de versão estável.

Padrão comum em empresas maduras: merge na main → deploy automático em dev/staging; criação de release/tag → deploy (manual ou automático) em produção.

Onde isso se conecta com GitOps / ArgoCD

🏗️
CI builda
A imagem é publicada em um registry.
📁
Repo de config
Guarda os manifests (YAML / Helm / Kustomize) separado do código.
🔁
ArgoCD puxa
Monitora o repo e faz pull das mudanças — ao contrário de pipelines que empurram (push).
Rollback no ArgoCD, na prática

É uma operação Git: reverter um commit no repositório de configuração, ou usar o histórico de sync da própria ferramenta.

// 07 — na prática

Como aplicar — 7 passos

  • 01
    Versionar tudo

    Código, configurações e schema de banco de dados precisam ter histórico de versões — senão não existe "estado anterior" pra voltar.

  • 02
    Escolher a estratégia de deploy certa

    A forma como você publica já define quão fácil é reverter: blue-green (troca instantânea entre dois ambientes), canary (libera pra poucos usuários primeiro) ou rolling (substitui aos poucos).

  • 03
    Automatizar no pipeline de CI/CD

    Rollback não deve depender de alguém lembrar o comando certo sob pressão — deve ser um botão/comando único ou disparado automaticamente.

  • 04
    Definir critérios objetivos de quando reverter

    Ex: "se erro passar de 2%, reverte automaticamente". Isso é decidido antes do deploy, não durante o incidente.

  • 05
    Garantir compatibilidade no banco de dados

    Usar o padrão expand-contract — a estrutura nova sem remover a antiga até ter certeza de que não vai precisar reverter.

  • 06
    Monitorar com métricas e alertas

    Sem observabilidade (logs, dashboards), o time nem percebe que precisa reverter a tempo.

  • 07
    Testar o processo regularmente

    Simular falhas de propósito pra garantir que o rollback funciona quando for realmente necessário.

// 08 — interdisciplinar

Como usaremos no Inventra

Como

O rollback deployment será aplicado no CI/CD do Inventra, após o processo de deploy de uma nova versão. Depois que o pipeline realizar o deploy, serão feitas validações para verificar se a aplicação está funcionando corretamente. Caso a nova versão apresente uma falha crítica, o pipeline poderá retornar automaticamente ou manualmente para a última versão estável, evitando que uma versão defeituosa permaneça em produção.

Onde

Cada versão do Inventra deverá ser identificada e mantida no histórico do repositório, permitindo que o pipeline de CI/CD saiba qual era a versão estável anterior.

exemplo — rollback no Inventra fluxo 
# versão v1.2.0 apresenta problema após o deploy
deploy("v1.2.0")  # falha crítica detectada
rollback(para="v1.1.0")  # pipeline restaura a última versão estável

# o processo também considera MongoDB e Redis,
# para evitar que uma alteração incompatível
# impeça a versão anterior de funcionar
// 09 — cenário real de mercado

Abordagem GitOps com Argo CD

O papel da prevenção: CI/CD e GMUD

Na maioria absoluta dos casos, um erro fatal em produção já é evitado pelas práticas de DevOps:

  • CI/CD (Continuous Integration / Continuous Deployment) — garante que o código passe por testes automatizados, análise de qualidade e validações de segurança antes de ser empacotado.
  • GMUD (Gestão de Mudanças) — adiciona uma camada de aprovação humana e estratégica. Exige plano detalhado, data, descrição do impacto e, obrigatoriamente, um plano de rollback.

Porém, essas práticas garantem 99% de segurança. O 1% restante envolve variáveis imprevisíveis de produção (falhas de rede, comportamento anômalo com dados reais, gargalos de infraestrutura). Para esse 1%, o plano de rollback abaixo é executado.

Passo a passo do rollback (GitOps)

Quando a versão 9.0.0 apresenta falha crítica em produção, o fluxo de reversão segue os princípios de GitOps:

  • 01
    Identificação e ação no repositório de infraestrutura

    O monitoramento alerta sobre o incidente com a versão 9.0.0. A equipe acessa o repositório de infraestrutura, localiza o YAML do Deployment afetado e altera manualmente a tag da imagem de 9.0.0 para a versão anterior estável, 8.4.4.

  • 02
    Pull Request (PR) e aprovação

    A alteração na tag gera um PR. Um colega da equipe revisa rapidamente para garantir que a sintaxe e a tag estão corretas. O PR é aprovado e o merge é feito na branch principal do repositório de infraestrutura.

  • 03
    Sincronização automática pelo Argo CD

    O Argo CD, que observa continuamente a branch principal, detecta a mudança (configuration drift): o estado desejado no Git agora exige a 8.4.4, mas o cluster está rodando a 9.0.0. Ele orquestra a criação de novos Pods com a 8.4.4 e, assim que estiverem saudáveis, encerra os Pods quebrados da 9.0.0.

  • 04
    Validação de produção

    A equipe verifica os endpoints da aplicação em produção e confirma que o sistema voltou a operar com a versão 8.4.4. O incidente é mitigado.

Imutabilidade: por que não apagamos a tag 9.0.0?

Mesmo após o rollback, a tag 9.0.0 jamais é apagada do repositório de código-fonte. O motivo é imutabilidade e rastreabilidade:

📜 Histórico

A tag quebrada serve como documentação viva — prova que os desenvolvedores tentaram a entrega e que houve um erro específico naquele exato código.

🔎 Post-mortem

A equipe precisará baixar o código exato da 9.0.0 para debugar, entender o que falhou em produção e aplicar a correção.

🌱 Evolução

Quando o erro for corrigido, uma nova tag será gerada (ex: 9.0.1 ou 9.1.0). A história do repositório permanece intacta.

// 10 — o custo de não ter um plano

Consequências da ausência de rollback

A ausência de um plano de rollback estruturado traz consequências críticas para a operação de tecnologia:

⏱️
Downtime prolongado

Sem uma reversão rápida e preparada, falhas em produção geram interrupções de serviço severas e comprometem a experiência do usuário.

🗄️
Risco à integridade dos dados

Atualizações malsucedidas (especialmente em bancos de dados relacionais) podem causar corrupção, resíduos indesejados ou perda irreversível de informações.

🔥
Sobrecarga e estresse da equipe

Sem um fluxo automatizado de retorno, engenharia e suporte investigam problemas sob extrema pressão, dependendo de "salas de guerra" e conhecimento informal de especialistas.

📉
Capacidade de entrega desperdiçada

O tempo gasto diagnosticando falhas e desfazendo alterações consome energia que deveria ir para novas funcionalidades — reduz o throughput e desalinha o planejamento de metas.

💔
Prejuízo à credibilidade

A instabilidade frequente e a demora na resolução de incidentes prejudicam a confiança de clientes e stakeholders no produto.

// 11 — quando um deployment dá errado

Casos reais

Para entender de verdade a importância do rollback, vale olhar para situações que aconteceram no mercado. Talvez o mais interessante seja perceber que um problema de deployment quase sempre precisa ser corrigido rápido — mas às vezes uma pequena alteração é suficiente para descambar numa crise.

CASO 1 GitHub — maio de 2023

No dia 10 de maio, o GitHub realizou uma alteração de configuração em um serviço interno responsável pelo gerenciamento dos bancos de dados do Git. A alteração tinha, inclusive, um objetivo positivo: evitar a saturação de conexões e já havia funcionado em outras partes da infraestrutura.

Porém, logo depois do início da distribuição da mudança, o cluster de banco de dados sofreu uma falha de failover. O sistema começou a apresentar problemas para realizar leituras e gravações.

Os engenheiros perceberam a instabilidade rapidamente e tentaram reverter a alteração. E aqui está o ponto mais importante para a nossa apresentação: o rollback também falhou, por causa de um erro de infraestrutura interna.

A equipe tinha identificado o problema e sabia qual era a ação esperada — voltar para uma configuração anterior. Mas a própria ferramenta que deveria servir como espécie de "saída de emergência" não funcionou. Isso fez com que a recuperação precisasse seguir um caminho muito mais complexo e manual: o GitHub realizou um failover gradual até conseguir restabelecer as operações.

O impacto foi grande: vários serviços da plataforma foram afetados, desenvolvedores tiveram problemas para ler e gravar dados, e pull requests e GitHub Actions também foram prejudicados. A investigação também encontrou problemas relacionados à versão do banco de dados utilizada naquele cluster e à sua configuração específica — corrigidos e reportados posteriormente aos mantenedores do banco.

A lição: não basta ter um rollback; é preciso garantir que ele realmente funcione quando tudo estiver dando errado.

CASO 2 Knight Capital — 2012

A Knight Capital era uma grande empresa do mercado financeiro americano, responsável por movimentar bilhões de dólares em negociações todos os dias. Para participar de um novo programa da bolsa de valores, a empresa precisava realizar um deployment em seu sistema de negociação — mas um dos oito servidores não recebeu corretamente o novo código.

Esse servidor ainda possuía uma funcionalidade antiga, chamada Power Peg, que havia sido desativada anos antes, mas continuava presente no sistema. Quando o mercado abriu, uma nova funcionalidade acabou ativando esse código antigo. O sistema começou a enviar ordens de compra e venda de maneira descontrolada.

Em poucos minutos, os engenheiros perceberam que havia algo muito errado. Mas eles não tinham um processo de rollback automatizado e seguro para aquela situação. Na tentativa de resolver o problema, a equipe removeu manualmente o novo código dos outros servidores que ainda estavam funcionando corretamente — e esse é o detalhe mais importante: a tentativa de rollback acabou espalhando o problema. O que estava inicialmente limitado a um servidor passou a afetar toda a infraestrutura de negociação.

Em aproximadamente 45 minutos, a Knight Capital acumulou bilhões de dólares em posições indesejadas e sofreu um prejuízo de aproximadamente $440 milhões. A empresa precisou receber uma injeção emergencial de capital e perdeu sua independência poucos meses depois, sendo posteriormente adquirida.

O que os dois casos têm em comum

No GitHub, o problema foi identificado rapidamente, mas o rollback não funcionou como esperado. Na Knight Capital, a empresa tentou reverter a situação manualmente, mas a ausência de um processo de rollback seguro contribuiu para agravar o problema. São situações diferentes, mas que apontam para a mesma conclusão: rollback não pode ser tratado como um detalhe que só será pensado quando alguma coisa der errado — ele precisa fazer parte do próprio planejamento do deployment.

Um bom processo precisa saber para qual versão voltar, como realizar essa reversão, como verificar se ela funcionou e, principalmente, precisa testar esse procedimento antes de depender dele em uma situação real. Porque, no fim, um deployment não termina quando colocamos uma nova versão em produção — ele termina quando temos segurança de que, se algo der errado, conseguimos recuperar o sistema.

Rollback não é plano B improvisado — é parte essencial do plano de produção

Reduz o tempo de exposição a uma falha, diminui o impacto para os usuários e dá à equipe uma maneira controlada de recuperar um sistema que apresentou problemas. Fazer um deployment e colocar uma mudança em um sistema real é garantir que, se essa mudança não funcionar, ainda existe uma forma segura de voltar.
